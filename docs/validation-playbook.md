# Edward 用户需求验证作战手册

> 目标（唯一）：回答这个问题 —— **一位开发者今天第一次知道 Edward，能否
> 在 5 分钟内理解其价值、15 分钟内亲自验证、并在下一次无人值守任务中愿意继续使用？**
>
> 若答案为是，增长有基础；若为否，当务之急是产品入口与实际价值，而非营销。
>
> 时间预算：45% 用户验证与采用体验 / 30% 核心可靠性 / 20% 社区与内容 / 5% 实验。
> 两周一轮，每天都在手册中留痕（见「数据记录表」）。

---

## 0. 定位与不做清单（先说清楚，防止执行漂移）

**一句话定位**：An independent runtime supervisor for unattended coding agents
（独立于模型之外、监督无人值守 Coding Agent 的运行时控制层）。

**明确不做/不承诺**：
- 不承诺「保证代码正确」——Edward 管运行过程，不管最终逻辑对错；
- 不承诺「阻止所有失控」——只承诺在**声明的检测范围**内发现、暂停/阻止并提供可审计记录；
- 不承诺强制隔离——进程外监督器无法阻止 Agent 绕开它直接执行；Enforcement 层是渐进目标；
- 不面向「偶发使用交互式 Agent 的用户」做第一市场。

**验证顺序**：真实使用者 → 亲自运行 → 明确门槛 → 再谈内容与挑战赛。

## 1. 目标用户筛选标准（ICP）

切入点：**痛点密度最高**的受众，而非受众规模最大。

### 三类优先画像

| 画像 | 特征 | 为什么优先 |
|---|---|---|
| **A. 重度 Agent 用户** | 同时/连续跑多个 Codex、Claude Code、pi 任务；每天 ≥2 次长任务 | 盯进度成本高，失控直接浪费时间 |
| **B. Agent 自动化开发者** | 在 CI、cron、脚本、自研框架中运行 Agent | 无人值守是默认状态，风险放大 |
| **C. AI 工程/平台团队** | 需要工具权限、成本、状态、失败复盘 | 有采购与制度化需求（第二阶段） |

### 筛选记分卡（每人 0–8 分，≥5 分才进入访谈）

| 问题 | 计分 |
|---|---|
| 每周使用 Coding Agent ≥ 3 次 | +1 |
| 有过 ≥30 分钟无人值守的 Agent 任务 | +2 |
| 过去 30 天内遇过：重复失败 / 状态丢失 / 预算失控 / 危险命令 / 长时间盯守（任一） | +2 |
| 有现成的拦停手段（脚本、超时、容器、人工轮询）但仍不满意 | +1 |
| 愿意提供一段脱敏真实轨迹 | +1 |
| 在 CI 或团队环境中运行 Agent | +1 |

**排除**：仅偶尔用 IDE 补全、以「AI 代码质量」为第一痛点、无真实长任务的开发者（礼貌收下联系方式，放入第二阶段名单）。

### 去哪里找（单兵可用渠道，按成本排序）

1. **已有接触点**：本机真实 session 的社区（V2EX /Agent 相关主题、即刻 AI 开发者圈、掘金评论区）；
2. **工具社区**：Claude Code、Codex、pi 的 Discord / GitHub Discussions / Issues 中讨论「agent 跑飞了」的人；
3. **中文技术社区**：V2EX（分享创造节点）、少数派、B站评论区（找发过 Agent 长任务的 UP）；
4. **英文渠道**（HN 无发帖权限，走评论区与私信）：r/ClaudeAI、r/ChatGPTCoding、相关 awesome 列表维护者；
5. **合作者转介**：JevTree/Chufan、Kev/Jared 生态内的实践者（一次转介顶十次冷启）。

## 2. 十五个访谈问题（30–40 分钟）

**铁律：只问过去发生的事，不问「你觉得有用吗」。** 对未来意愿的礼貌性肯定没有证据价值。

### A. 现状与频率（1–4）
1. 过去一周，你跑了哪些 Coding Agent 任务？最长的一次跑了多久？
2. 其中有多少是你**没有一直盯着屏幕**的？
3. 你的 Agent 任务通常以什么方式结束——自己停、你做决定停、还是超时/报错停？
4. 你现在怎么知道一个长任务「进展正常」？

### B. 事故考古（5–9）—— 最有价值的部分
5. 最近一次 Agent 让你**不得不介入**的任务是什么？当时发生了什么？
6. 你是**怎么发现的**？如果没发现会怎样（最坏后果）？
7. 有没有一次是**你没发现**、事后才意识到跑偏的？
8. 那次损失了什么：时间 / 钱 / 数据 / 信任？
9. 事后你改了什么流程来防止它再发生？

### C. 现有替代方案（10–12）
10. 你现在用什么防止这类问题——超时？容器？预算上限？定期看日志？纯人盯？
11. 它为什么还不够？在哪一步失效？
12. 如果让 Agent 自己「报告状态」，你信任它报告的内容吗？（引出「外部监督 vs 自我报告」）

### D. 安装意愿与拒绝理由（13–15）
13. 如果有一个外部进程，能在你的 Agent 跑飞时暂停它并留下记录，你愿意在**哪个具体任务**上先试？
14. 什么会让你**拒绝安装**？（权限顾虑、误报、恢复风险、公司规定……）
15. 你希望它绝对不能做什么？（划定我们的诚实边界）

**收尾请求**：要一段脱敏轨迹 + 约一次「亲手运行」的时间。

## 3. 竞品与替代方案对照（访谈时随手查）

最大的对手不是别家产品，而是「**什么都不装**」。

| 替代方案 | 它擅长 | 它的缺口（我们的切入点） | 我们的证据 |
|---|---|---|---|
| **不装**：超时 + diff + 测试 + 人盯 | 零成本、够用于短任务 | 跨轮次累积的失控（循环、预算、停滞、越权写入）无人工盯守时无信号 | StepShield 留出集；56 真实会话 2663 步零语义误报 |
| **可观测性平台**（Langfuse / LangSmith / Phoenix） | 追踪、评估、调试界面 | 只回答「发生了什么」，不做「现在该不该停」，没有真正的干预与恢复 | 决策层 + PAUSE/CANCEL + `edward replay` |
| **CI / 沙箱 / 策略门禁** | 隔离、权限、审批 | 静态边界，不感知**跨多轮**的异常累积；Agent 可在边界内跑飞 | 状态引擎跨轮次判断（预算/循环/收敛停滞） |
| **Agent 自带上限**（--max-turns、budget） | 简单粗暴有效 | 只看单维预算，不看失败模式；触发时无证据、不可恢复 | 可恢复暂停 + 签名回执 + 干预原因 |
| **其他监督器**（若有） | 视具体产品 | ——对照测试入口：`edward bench` + 公开基准格式 | BENCHMARK.md 全套复现命令 |

**应答模板**（被问「和 X 有何不同」）：不贬低 X，指出层次差异（Observability / Runtime supervision / Enforcement 三层），说明 Edward 只占第二层并诚实标注第三层的边界。

## 4. 真实任务测试脚本（15 分钟验证路径）

对每位受访者当面/屏幕共享执行一次，记录每一步的**卡点**。

### 步骤（含预期耗时与观察点）

| # | 动作 | 预期 | 观察点（记录用） |
|---|---|---|---|
| 1 | `pipx install edward-guard`（或 pip） | 装完有 `edward` 命令 | 安装是否报错；是否需要解释 |
| 2 | `edward init`（三问） | 产出 policy + 下一步提示 | 用户是否读懂三个问题 |
| 3 | `edward demo` | 六个场景 PASS + 三行 next steps | **看用户能否说出「它在检测什么」** |
| 4 | `edward wrap --no-scorer -- pi "<真实小任务>"` | 实时日志 + 结束汇总 | 是否理解 trigger/decision 两行 |
| 5 | 触发一次干预（可用现有 policy 的 stall/dangerous 场景） | PAUSE 或阻断 + 反馈文件 | 是否理解「为什么被停」 |
| 6 | `edward replay` → 打开 HTML | 深色收据页 | **是否愿意把这张图发给同事** |
| 7 | （可选）`edward doctor --probe` | 语义评分器一回环 OK | 只有装本地 scorer 的用户需要 |
| 8 | 询问：下一个无人值守任务是否愿意再跑一次 | 明确 yes/no/条件 | 记原话，不追问 |

### 三个必须记录的数字/事实
1. **Time-to-first-run**：从敲下安装到第一次成功 wrap 的分钟数（目标 ≤10）；
2. **理解度**：用户能否不看文档说出 (a) 它监控什么 (b) 停下来的原因是什么；
3. **真实误报**：本次真实任务中是否发生误报（有则保存 `edward replay` 页）。

### 演示降级路径（如果现场出问题）
- 无 GPU / 无 scorer：`--no-scorer` 全程可用，规则层照样拦危险命令；
- 无 pi：用 `--agent claude` 或任意命令 `edward wrap --no-scorer -- <cmd>`；
- 网络差：`edward demo --live-scorer --offline` 完全离线。

## 5. 数据记录表（每位受访者一行，建议 CSV）

```
编号, 日期, 来源渠道, 画像(A/B/C), 筛选得分,
周频次, 最长无人值守时长, 主要痛点(原话),
访谈关键引语1, 访谈关键引语2, 拒绝理由,
是否亲手运行(y/n), time-to-first-run(分钟), 理解度(y/n/部分),
本次误报(y/n), 恢复是否尝试(y/n), 第二周复用(y/n/未知),
可观测收益(原话或数字), 后续动作(试用/转介/暂缓)
```

**证据等级**（写结论时标注）：
- L1 原话声称「有用」→ 不计分；
- L2 亲手跑完测试脚本 → 计分；
- L3 第二周在真实任务中复用 → 核心证据；
- L4 可测量的收益（少盯 N 小时 / 拦下 N 次 / 止损金额）→ 最有说服力。

## 6. 继续 / 调整 / 转向 决策门槛（第 14 天评估）

**样本要求**：15 位合格受访者（筛选 ≥5 分），其中 ≥10 位完成访谈、≥8 位完成测试脚本。

| 结果 | 判断 | 行动 |
|---|---|---|
| ≥5 位跑真实任务，≥3 位第二周复用，且有可解释收益（L3/L4） | **继续当前定位** | 进入内容与案例发布阶段（第 15–30 天路线） |
| 用户承认痛点但拒绝独立监督器（比例 >50%） | **调整入口** | 测 CI Action、MCP 集成、现有工作流包装等低摩擦形态；不先加功能 |
| 用户高频用 Agent 但无明显监督需求，痛点集中在代码验证/变更审查/任务状态 | **重新审视定位** | 考虑转向相邻高频问题；停止按现假设投入 |
| 无人愿意跑测试脚本（>70%） | **产品入口失败** | 回到「5 分钟理解」，只做入口与演示，暂停一切外部宣传 |

**反模式警示**：若 10 位用户里 8 位觉得问题不重要，不要把结论解释成「营销没做好」——那是首个市场选错。

## 7. 三十天节奏（与手册挂钩）

| 时间 | 首要任务 | 交付物 |
|---|---|---|
| 第 1–3 天 | 选定首要人群与场景 | 一页 ICP + 痛点假设（本手册第 1 节） |
| 第 4–7 天 | 打磨首次运行与演示路径 | 可复制 Quickstart、录屏、`edward replay` 回执样例 |
| 第 8–14 天 | 访谈 + 观察真实运行 | 10–15 次访谈、≥8 次亲手运行（第 2、4 节） |
| 第 15–21 天 | 按反馈修最大摩擦 | 采用率、误报、恢复、成本数据；第 6 节门槛评估 |
| 第 22–26 天 | 发布案例与可复现测试 | 一篇技术报告 + 一段演示 + 完整复现命令 |
| 第 27–30 天 | 评估渠道与留存 | 是否继续当前定位的决策记录 |

**暂缓清单**（除非访谈推翻）：云端 Fleet Console、大规模 Agent Failure Challenge、多平台社媒运营（先找出 1–2 个能带来真实试用的渠道）。

## 8. 一键开场检查（执行当天）

```bash
# 1) 环境自检：确保演示路径无风险
edward demo                                   # 应 PASS，并打印 next steps
edward doctor --probe                          # 有本地 scorer 时
# 2) 准备一块「脏现场」用于演示干预与回执
edward wrap --no-scorer -- bash -c 'for i in $(seq 1 50); do echo "loop $i"; sleep 1; done'
edward replay                                  # 生成 HTML 收据页，提前打开确认样式
# 3) 准备三个真实小任务（5–10 分钟内可完成），避免现场编任务
```

**访谈前 60 秒**：把「5 分钟理解 / 15 分钟验证」写在便签上，全程只用受访者的语言，不用
State Engine / MSS / 语义评分器 等内部术语。
